# 上下文恢复的进度与完成状态

## 1. 概述

### 1.1 问题

长任务触发上下文超限后，后台正在压缩会话，界面却一直显示“正在分析”。用户无法判断任务是否仍在恢复。

实机续跑还发现：清单文件已生成，但正常回复引用故障示例时，会话又被标成失败。

### 1.2 根因

正常压缩会发送开始、结束事件，端侧已有对应提示。超限后的恢复由另一条运行路径执行，没有发送这些事件，因此现有界面无法展示压缩过程。

完成状态误报来自对整段回复搜索错误文字。正常答案中的故障示例也会命中，随后被错误地当作运行失败处理。

## 2. 用户场景

用户提交较长的项目资料，模型拒绝本轮输入后，系统自动压缩并尝试继续。等待期间应看到压缩提示；完成、失败或取消后应退出该状态。

## 3. 功能需求

- 恢复性压缩开始时，复用现有的上下文压缩提示和进度动画。
- 仅在压缩结果已被接受后显示完成；失败或取消不能显示成功。
- 保持原有恢复次数、会话历史和取消行为。
- 正常答案引用错误说明时仍可完成；真正的运行失败提示继续展示。

## 4. 实现方案

在固定版本的 OpenClaw 超限恢复入口补齐已有的压缩事件。使用统一事件通道关联当前运行，在结束路径清理状态，不根据日志文本猜测进度，也不增加一套界面计时状态。

在端侧适配层将兼容性的失败文案识别收窄为已知提示开头，保留运行时警告前缀的支持，避免把回答正文中的引用当作失败。明确的错误事件处理保持原有行为。

## 5. 边界情况

摘要请求失败、执行抛错或用户取消时，都结束压缩状态。未实际进入压缩的请求不发送该提示。压缩完成不代表整个任务已经完成，后续回复仍由原任务流程驱动。

## 6. 验收标准

- 真实长资料场景中可见压缩过程，成功后继续完成原任务。
- 失败、取消均不会永久停留在压缩中或误报成功。
- 正常对话及连续工具调用不受影响；原始输入保留且不重复插入。
- 完整任务回复中可以引用故障说明，不会出现已交付文件却误报失败的情况。

**OpenClaw IM 配置保留与 Windows 正常退出：用户侧冒烟回验**

修复分支：`fix/openclaw-im-config-lifecycle`；目标分支：`feat/openclaw-v2026.8.1`。
优先在 Windows、OpenClaw v2026.8.1、QQ 插件 2.0.1 上回验，预计 10–15 分钟。

此次验收关注两点：模型配置暂时无法解析时保留已有 IM 配置；Windows 正常停止网关时执行清理，避免连续重启被误记为崩溃循环。模型不可用期间允许无法生成回复；模型恢复后的新消息应自动恢复收发。

```text

5. 再执行一次“退出登录 → 正常退出客户端 → 重开 → 登录同一账号 → 发送新消息”，覆盖两个修复共同作用的场景。
```

**建议回验顺序**

| 步骤 | 用户操作 | 预期与通过条件 |
| --- | --- | --- |
| 1. 基线 | 打开 QQ 设置，记录实例、启用状态及绑定 Agent，发送基线消息。 | QQ 收到对应编号的回复；龙虾出现本次用户消息与回复，归属正确 Agent。基线失败则先定位环境问题。 |
| 2. 模型不可用窗口 | 仅使用内置服务端模型时，从账号菜单退出登录。若还有自定义 provider 可用，先记录其设置并临时禁用；退出后等待配置同步，再重新登录。 | 用日志及生成配置确认命中“无可解析模型”的窗口；已有 `channels.qqbot`、`bindings`、`agents`、网关认证仍保留，`models` 可被移除。只有界面设置没丢，不能单独证明网关配置未丢。 |
| 3. 自动恢复 | 重新登录同一账号，等待模型加载及 QQ 就绪，直接发恢复消息。 | 无需重新填写 QQ 凭据、切换 IM 开关、重新保存 IM 配置或手动修复，即可回复新编号；实例及绑定保持一致。模型不可用期间不要求成功回复，也不要求恢复后补发那段时间的旧消息。 |
| 4. 连续正常启停 | 等回复结束，用托盘“退出”，待客户端退出后重开；每轮就绪后发送新编号，尽量五分钟内完成四轮。 | 四轮都能恢复收发，编号对应正确；没有新消息长期静默、重复回复或错误 Agent。确认每轮真的停止并重启了网关；只关闭窗口或刷新页面不算。 |
| 5. 组合场景 | 退出登录并等待模型配置同步，再从托盘退出；重开、登录同一账号、等待就绪后发送组合消息。 | 原有 QQ 实例、Agent 绑定自动恢复，新消息正常回复，无需重配。 |
| 6. 可选扩展 | 有其他已配置 IM 时，在模型恢复后及第四轮启动后各发一次独立编号；有第二个 QQ 实例时也检查其路由。 | 各实例独立恢复，不串号、不改变绑定。新装且从未配置模型的环境可另查网关能否正常启动。 |

等待标准：网关和 QQ 就绪后再发消息；简单文本超过 60 秒无回复时，记录为超时并采集证据。60 秒是本次烟测的观察窗口，后续用日志区分模型响应慢、QQ 未收消息及回复发送失败。

**如何判断命中了修复路径**

模型缺失分支可由“登录态清理 / 服务端模型清空 → 无匹配模型 → 配置同步”这一时间线辅助确认。Windows 标准配置路径为 `%APPDATA%/LobsterAI/openclaw/state/openclaw.json`，若启动日志显示不同的 userData 路径，以实际路径为准。比较退出登录前、模型缺失期间和恢复后的配置段，避免输出凭据。仅观察设置页不足以检验此修复，因为旧问题丢失的是生成的 OpenClaw 配置。

正常启停时，开发侧可按当轮 PID、时间对齐 `requesting graceful shutdown`、`signal SIGINT received` 和正常退出事件。有权读取运行时状态库时，再检查 `gateway_boot_lifecycle` 对应记录的 `outcome = clean_stop` 且 `completed_at_ms` 非空。只统计本次测试时间范围，历史不洁退出记录可能仍处于五分钟窗口内；此时先记录历史影响，等待窗口结束后重测，不清空状态库。

留意本次新增的 `suppressing channel/provider autostart`、`gateway shutdown exceeded` 或 `SIGKILL`。单条日志缺失不足以判失败，应结合进程退出状态、启动记录和实际收发。正常停止仍有 6 秒清理、2 秒强制退出等待的兜底；本轮主流程在空闲时退出，不将强杀或长任务未结束作为正常清理的验收条件。

# OpenClaw 网关重启后 IM 恢复异常修复设计文档

## 1. 概述

### 1.1 问题

在 OpenClaw v2026.8.1、QQ 插件 2.0.1 环境下，退出登录等配置变更触发网关重启后，出现两类异常：

- QQ 频道未自动恢复，手机发送新消息后没有回复；网关日志提示 `restart-loop breaker tripped`。
- QQ 已恢复收发，但 LobsterAI 桌面没有同步后续消息，已有会话停留在重启前的历史。

此前 [#2632](https://github.com/netease-youdao/LobsterAI/pull/2632) 已保留模型暂不可用时的 IM 配置，并通过 IPC 让 Windows 网关进入正常关闭流程。本次补齐 QQ 插件退出处理和桌面客户端重连后的历史同步，归于同一恢复主题；两者根因独立。

### 1.2 根因

**QQ 插件提前退出宿主进程。** QQ 2.0.1 在 `setQQBotRuntime()` 中注册信号处理函数，收到 `SIGINT` 或 `SIGTERM` 后刷新引用索引并直接调用 `process.exit(0)`。OpenClaw 的信号处理需要异步关闭频道并执行 `completeBoot()`，插件的主动退出打断了这一流程。即使父进程观察到退出码为 0，启动记录仍可能未完成；五分钟内累积三次后，网关保护机制抑制频道自动启动。

**桌面重连没有恢复历史同步。** 配置重启会主动断开客户端并清除频道同步定时器。普通 RPC 可以重新建立连接和订阅 `sessions.changed`，但原握手路径没有恢复定时器，已有客户端的 `connectGatewayIfNeeded()` 也直接返回。事件触发的补同步依赖该定时器存在，因此桌面只能更新运行状态，无法补入历史消息。

以下证据来自 2026-09-09 本机主进程、网关日志及状态库只读查询，时间为 UTC+8：

| 场景 | 关键证据 | 结论 |
| --- | --- | --- |
| 插件退出 | 11:51:10、11:51:37 收到 `SIGINT` 后以 `code=0` 退出，`gateway_boot_lifecycle` 对应记录的完成时间和结果为空；此前另有一次强制退出。11:51:45 触发三次不洁启动保护。 | 仅检查退出码无法证明正常收尾；生成配置中的 QQ 账号及 Agent 绑定仍在。 |
| 桌面同步 | 14:00:37 配置重启断开客户端，14:01:30 普通连接恢复订阅；14:01:57 至 14:03:25 网关完成的新回复已写入 OpenClaw 状态库，桌面仍只有截至 14:00:22 的 6 条消息。 | 回复已经生成，缺失发生在桌面历史同步阶段。此轮三次网关停止均为 `clean_stop`，插件退出修复已生效。 |

## 2. 用户场景

| 场景 | 预期行为 |
| --- | --- |
| 配置变更触发网关重启，或用户正常退出并重开客户端 | QQ 插件允许网关完成清理，正常停止不会新增不洁启动记录；网关重新就绪后恢复频道收发。 |
| 网关重启后，用户仅在手机 QQ 发送消息 | 桌面主动恢复连接和历史同步，无需从 PC 发送消息或重新保存 IM 配置。 |
| 切换模型或普通 RPC 先恢复网关连接 | 该连接同时恢复历史同步，补入断线期间已经生成的消息。 |
| 多个入口重复请求连接 | 复用已有客户端及同步定时器，保持消息去重和原会话归属。 |

## 3. 功能需求

1. QQ 插件保留关闭时的数据刷新，由 OpenClaw 统一负责进程退出及启动记录收尾。
2. 插件适配覆盖新下载和已有缓存的准备路径，重复执行结果稳定；无法识别发布代码时明确报错。
3. 配置重启成功后恢复桌面网关连接，握手完成及已有客户端路径都能恢复频道发现和历史同步。
4. 沿用现有历史对齐、事件补同步和定时补同步机制，不产生重复消息或多个同步定时器。

## 4. 实现方案

### 4.1 由网关管理 QQ 插件退出

在 `scripts/openclaw-plugin-preparers/qqbot.cjs` 的现有打包准备流程中，适配已锁定的 QQ 2.0.1 发布入口 `dist/index.cjs`：

- 保留 `beforeExit` 刷新，将 `SIGINT`、`SIGTERM` 处理改为仅刷新，移除其中的 `process.exit(0)`。
- 增加 `exit` 刷新，覆盖宿主最终调用 `process.exit()`、不会触发 `beforeExit` 的路径。
- 检查原始或已适配的处理函数形态，兼容 LF、CRLF；匹配不唯一或代码形态变化时停止打包并提示检查。

适配发生在 LobsterAI 的插件准备边界，无需修改上游网关源码。开发环境已有运行时需执行 `npm run openclaw:plugins` 并重开客户端；完整运行时构建已包含插件同步步骤。

### 4.2 重连时恢复桌面消息同步

- `src/main/main.ts`：配置驱动的 `restartGateway()` 成功后调用 `connectGatewayIfNeeded()`；退出应用或数据恢复期间不发起该重连。
- `src/main/libs/agentEngine/openclawRuntimeAdapter.ts`：当前客户端握手成功后恢复频道同步；已有客户端路径也调用 `startChannelPolling()`。
- `startChannelPolling()` 保持幂等，复用已有定时器，并在首次恢复时立即发现频道会话和对齐历史。

新增回归覆盖位于 `tests/prepare-openclaw-qqbot.test.ts` 和 `src/main/libs/agentEngine/openclawRuntimeAdapter.test.ts`。

## 5. 边界情况

| 场景 | 处理方式 |
| --- | --- |
| 网关清理超时或被外部强杀 | 保留现有 6 秒清理超时及强制终止兜底；不保证这类退出会记录为 `clean_stop`。 |
| 历史不洁退出仍处于保护窗口 | 保留 OpenClaw 原有保护机制，不清空启动记录或强行绕过自动启动抑制。 |
| 退出登录后仍选用套餐模型 | 模型请求可能失败；模型可用性与频道连接、桌面同步分别判断，不由本次修复改变认证或自动切换模型。 |
| 连接恢复但漏掉会话变更事件 | 由现有 10 秒轮询补齐历史，并沿用现有去重逻辑。 |
| 应用退出或数据恢复 | 保留原断开连接及停止同步的流程，不因配置重启完成而重新拉起客户端。 |
| QQ 插件后续升级 | 重新审查发布入口的关闭逻辑；不对未知代码形态静默应用补丁。 |

## 6. 验收标准

1. 加载真实 QQ 插件、空闲状态下连续正常启停四次，对应启动记录均为 `clean_stop`，不因插件主动退出新增重启循环保护。
2. 配置重启后，仅通过手机 QQ 发送新消息，桌面能自动同步；断线期间已生成的消息也能补齐，无需手动重连。
3. 普通 RPC、模型切换及专用重连入口均恢复同步；重复调用不增加定时器，不重复插入消息。
4. 正常会话事件触发及时补同步，遗漏事件时可在一个轮询周期及请求耗时内补齐；消息归属保持一致。

### 已完成的验证

以下为代码修复时完成的验证记录：

- QQ 插件准备、安装、宿主依赖及进程停止相关测试共 39 项通过；插件安装测试存在既有 Node `DEP0190` 提示。
- 运行时适配器、频道会话同步、网关重启监督及进程停止相关测试共 306 项通过；新增 3 个重连回归场景修复前失败、修复后通过。
- 修改的 TypeScript 文件通过 ESLint，Electron TypeScript 编译、打包脚本语法检查及差异空白检查通过。
- Windows 隔离运行时加载原版 QQ 插件，复现退出码为 0 而启动记录未完成；加载适配后的插件连续启停四次，全部记录为 `clean_stop`。
- 真实 OpenClaw 网关配合编译后的桌面适配器，以合成 QQ 会话验证配置重启和普通 RPC 重连，消息分别由 1 条补至 2 条、由 2 条补至 3 条，并触发桌面刷新；两次停止均为 `clean_stop`。

隔离运行时验证未连接真实 QQ 账号；用户后续回验已确认 QQ 可以正常会话，重新登录后可以继续对话，失败消息也已同步到桌面。上述测试数量为各测试集合独立执行的结果，不代表全仓测试通过。

## 1. 结论

移除“我的文件”本地产物页和云端共享页工具栏下方横贯内容区的蓝色加载条，改为按操作来源就近反馈：

- 搜索请求：搜索框左侧的放大镜延迟替换为中性色微型转圈。
- 筛选请求：在筛选控件旁的固定状态槽中显示微型转圈。
- 切换数据源：有目标数据快照时在当前来源标签旁反馈；没有快照时使用现有首屏骨架。
- 云端手动刷新：仅让用户点击的刷新图标旋转。
- 本地后台刷新：默认静默完成，失败时才使用现有错误反馈。
- 加载下一页：继续使用列表底部的分页转圈。
- 首次进入且没有任何可展示数据：继续使用现有首屏骨架。

搜索和筛选时保留上一份同作用域结果，不遮罩、不压暗、不清空列表，也不阻断搜索框和安全的文件操作。请求在 200ms 内完成时不显示加载反馈，从而消除短请求的闪烁。

本方案只调整客户端展示状态和交互，不改变查询参数、IPC、服务端接口、SQLite/MySQL 数据模型及分页协议。

## 2. 背景与问题

### 2.1 用户可见现象

当前在“我的文件”中输入搜索词或改变筛选条件后，工具栏底部会出现一条完整宽度、静态的蓝色细线。该细线存在以下问题：

1. 外观接近浏览器页面加载进度条，但它不表达真实进度，容易形成错误预期。
2. 反馈横贯整个内容区，视觉权重高于触发请求的搜索框或筛选控件。
3. 快速请求也会短暂出现，产生蓝线闪烁。
4. 搜索、筛选、手动刷新和后台刷新共用同一种反馈，用户无法理解是谁触发了加载。
5. 列表本身仍然保留旧内容，顶部蓝线却暗示页面正在整体切换，两者语义不一致。

### 2.2 当前实现定位

客户端当前已经具备可复用的正确基础：

- 搜索输入有 300ms 防抖。
- 本地与云端数据分别保留最近一次成功结果。
- 查询通过 request ID 防止旧请求覆盖新请求。
- 加载状态已区分首次加载、重新校验、主动刷新和追加分页。
- 首屏存在骨架屏，分页存在底部转圈，云端存在独立刷新按钮。

问题主要来自展示层：

- `LibraryView.tsx` 将重新校验和主动刷新统一折叠为 `refreshing`。
- `LibraryView.tsx` 与 `LibrarySharedFilesView.tsx` 都在该布尔值为真时绘制同一条全宽蓝线。
- 展示层没有携带“搜索、筛选、来源切换、手动刷新、后台刷新”等触发原因，因此无法就近反馈。
- 反馈没有延迟门槛，请求足够快时也会形成瞬时闪烁。

### 2.3 与 2026-08-17 主规格的关系

[`2026-08-17-library-design.md`](../../features/library/2026-08-17-library-design.md) 保留为历史主规格。本文件是当前实现基础上的加载反馈增量设计；仅在以下内容冲突时，以本文件为准：

- 加载状态沿用当前代码中的 `Initial / Settled / Revalidating / Refreshing / Appending`，不要求为本次修复新增 `transitioning` 状态。
- 可见反馈延迟由旧设计的 150ms 调整为 200ms。
- 本次修复不以查询快照 LRU、通用 reducer 或重做结构化骨架屏为前置条件。
- 同来源、同账号作用域中的上一份结果保持可交互，不再要求整体只读。
- “低干扰工具栏进度”具体收敛为上下文微型转圈，不再使用全宽蓝色线。

除上述加载反馈范围外，主规格中的信息架构、数据来源、文件操作、权限、分页、分享及安全约束继续有效。

## 3. 目标与非目标

### 3.1 设计目标

1. 彻底移除本地页和云端页的全宽蓝色加载条。
2. 让反馈靠近触发操作的位置，用户能理解当前发生的是搜索、筛选、刷新还是分页。
3. 快请求无闪烁，慢请求有明确反馈，长请求有可理解的状态文本。
4. 搜索和筛选期间保持内容稳定，避免列表清空、骨架切换和滚动跳动。
5. 保持最新请求优先，不能因视觉延迟引入旧结果覆盖。
6. 本地和云端体验一致，但尊重两类数据源已有的独立能力。
7. 满足键盘、读屏和减少动态效果设置下的可访问性要求。

### 3.2 非目标

- 不优化本地 SQLite 查询或云端接口耗时。
- 不改变 300ms 搜索防抖。
- 不新增服务端接口、字段、排序方式或分页协议。
- 不调整本地索引事件、云端分享逻辑或文件操作权限。
- 不重做当前首屏骨架的视觉样式。
- 不引入进度百分比；当前请求没有可信的可计算进度。
- 不修改 portal、admin 或服务端项目。
- 不新增或变更数据库表；线上 MySQL 5.7 兼容性不受影响。

## 4. 体验原则

### 4.1 反馈跟随操作来源

加载提示应出现在用户刚刚操作的控件附近。搜索发生在搜索框，筛选发生在筛选区，刷新发生在刷新按钮，分页发生在列表底部。

### 4.2 稳定内容优先

只要当前作用域已有成功结果，重新查询期间就保留它。加载反馈不应改变内容区高度、列表布局、选中项或滚动位置。

### 4.3 只在等待可感知时出现

请求开始后先等待 200ms：

- 200ms 内完成：不显示转圈。
- 超过 200ms：显示与触发原因对应的微型反馈。
- 超过 1000ms：桌面宽度下增加简短状态文字；窄窗口只保留转圈和读屏文本。

直接点击“刷新”属于需要即时确认的显式操作，刷新图标从点击时开始旋转，不受 200ms 延迟限制。

### 4.4 不伪装成确定进度

所有请求均为不确定时长，使用循环转圈而不是长度变化的进度条，不显示未经计算的百分比。

### 4.5 作用域隔离

只有来源和账号作用域一致的数据可以作为重新校验期间的旧结果：

- 本地产物只能复用本地产物快照。
- 云端共享只能复用当前云端账号/团队作用域的快照。
- 切换账号、退出登录或权限变化后，不得展示上一账号的数据。

## 5. 场景与期望行为

| 场景 | 内容区 | 反馈位置 | 出现时机 | 完成后 |
| --- | --- | --- | --- | --- |
| 首次进入，无任何快照 | 保持稳定占位，随后显示现有骨架 | 内容区 | 请求超过 200ms | 替换为结果或空状态 |
| 搜索，已有同作用域结果 | 保留并允许操作旧结果 | 搜索框左侧图标 | 请求超过 200ms | 原子替换结果并滚到顶部 |
| 类别/状态/收藏筛选 | 保留并允许操作旧结果 | 筛选区固定状态槽 | 请求超过 200ms | 原子替换结果并滚到顶部 |
| 切换本地/云端，有目标来源快照 | 立即显示目标来源最近结果 | 当前来源标签旁 | 请求超过 200ms | 原子替换，不跨来源复用 |
| 切换本地/云端，无目标来源快照 | 不显示另一来源数据 | 内容区骨架 | 请求超过 200ms | 显示结果、空状态或错误 |
| 云端手动刷新 | 保留当前结果 | 被点击的刷新按钮 | 点击后立即 | 停止旋转并保留滚动位置 |
| 本地索引后台刷新 | 保留当前结果 | 默认无可见反馈 | 不显示 | 无声更新；失败才提示 |
| 加载下一页 | 保留已有项目 | 列表底部 | 请求开始后立即 | 将新项目追加到底部 |
| 快速连续输入 | 保留当前已提交结果 | 仅为最新请求反馈 | 最新请求超过 200ms | 只有最新请求可以提交 |
| 重新校验失败，有旧结果 | 保留旧结果 | 现有错误区域/重试入口 | 失败时 | 标记“结果未更新”，允许重试 |
| 首次加载失败，无旧结果 | 不伪装成空列表 | 现有整页错误状态 | 失败时 | 允许重试 |

## 6. 视觉与交互设计

### 6.1 搜索框反馈

- 空闲态：左侧显示现有放大镜。
- 搜索请求超过 200ms：放大镜原位替换为 14px 中性色转圈。
- 清空按钮始终保留，不能与转圈互相替换。
- 输入框宽度、内边距和清空按钮位置保持不变，避免布局抖动。
- 用户继续输入时保持焦点；新防抖请求取代旧请求，转圈计时以新请求为准。
- 搜索结果返回前，不更改输入框中的当前文本。

### 6.2 筛选反馈

- 在筛选控件组之后预留固定的活动状态槽。
- 宽窗口状态槽宽度建议为 80px，可容纳 14px 转圈和“更新中”短文本。
- 窄窗口只保留 16px 图标槽，状态文字对视觉隐藏但供读屏读取。
- 前 200ms 状态槽为空；200ms 后显示转圈；1000ms 后显示“更新中”。
- 不使用替换下拉箭头的方式，避免削弱控件仍可继续操作的暗示。

### 6.3 来源切换反馈

- 目标来源已有安全快照时，立即切换到该快照；超过 200ms 后在激活来源标签旁显示微型转圈。
- 目标来源无快照时，不得短暂显示当前来源内容；超过 200ms 后显示现有首屏骨架。
- 账号作用域变化按“无安全快照”处理，即使内存里仍有上一账号的云端数据。

### 6.4 刷新反馈

- 云端手动刷新继续使用现有刷新按钮，点击后图标立即旋转。
- 手动刷新期间按钮设置为不可重复触发，但搜索框和列表不需要整体禁用。
- 本地索引事件触发的后台刷新默认静默，不显示搜索转圈、筛选转圈或刷新图标动画。
- 后台刷新失败沿用现有错误提示；不能为了显示错误而清空成功结果。

### 6.5 分页反馈

- 保留当前列表底部转圈，不在工具栏重复反馈。
- 分页期间已加载项目保持可操作。
- 搜索、筛选或来源切换发生时，当前分页请求失效；其晚到结果不得追加到新查询。

### 6.6 颜色与动效

- 转圈使用中性色，例如 `text-muted-foreground`，不使用高饱和主蓝色。
- 图标尺寸统一为 14px，线宽约 1.5px。
- 建议旋转周期为 600–800ms，避免过快造成焦躁。
- 不增加闪烁、呼吸或横向扫光效果。
- 在 `prefers-reduced-motion: reduce` 下停止持续旋转，显示静态等待图标并保留状态文字。

### 6.7 长等待文本

超过 1000ms 时显示简短文本：

| 原因 | 中文 | 英文 |
| --- | --- | --- |
| 搜索 | 正在搜索 | Searching |
| 筛选/来源重新校验 | 更新中 | Updating |
| 手动刷新 | 刷新中 | Refreshing |

文本使用现有国际化能力，中文和英文必须同时补齐。状态槽预留空间后再显示文字，因此不能推动搜索框或筛选控件位移。

## 7. 状态模型

### 7.1 保留现有阶段

继续使用 `libraryLocalQueryState.ts` 中已有阶段：

| 阶段 | 含义 | 是否有已提交结果 |
| --- | --- | --- |
| `Initial` | 当前作用域首次查询 | 否 |
| `Settled` | 当前结果已提交 | 是或已确认空 |
| `Revalidating` | 查询条件变化，重新获取结果 | 通常是 |
| `Refreshing` | 用户手动刷新或后台数据变化 | 通常是 |
| `Appending` | 获取下一页 | 是 |

本次不把阶段重命名，也不额外引入通用状态机 reducer。

### 7.2 新增触发原因

展示层需要在阶段之外记录触发原因，建议集中定义 `LibraryLoadCause`：

| 原因 | 典型触发 |
| --- | --- |
| `Initial` | 首次进入当前作用域 |
| `Search` | 防抖搜索词提交 |
| `Filter` | 类别、可用状态、收藏或排序变化 |
| `SourceSwitch` | 本地产物与云端共享切换 |
| `AccountSwitch` | 登录账号或云端作用域变化 |
| `ManualRefresh` | 点击云端刷新按钮 |
| `BackgroundRefresh` | 本地索引事件或被动同步 |
| `Append` | 到达列表底部并加载下一页 |

阶段描述“请求正在做什么”，原因描述“为何开始请求”。二者不能再合并成单一 `refreshing` 布尔值。

### 7.3 展示派生

建议用纯函数从阶段、原因、是否有安全快照和等待时长派生展示：

| 派生值 | 用途 |
| --- | --- |
| `showInitialSkeleton` | 无安全快照且首次/跨作用域请求超过 200ms |
| `showSearchActivity` | 搜索重新校验超过 200ms |
| `showFilterActivity` | 筛选重新校验超过 200ms |
| `showSourceActivity` | 有目标来源快照的来源切换超过 200ms |
| `showManualRefreshActivity` | 手动刷新，从点击起立即为真 |
| `showAppendActivity` | 追加分页请求进行中 |
| `announceLongWait` | 可见请求超过 1000ms |
| `ariaBusy` | 当前作用域存在用户可感知请求 |

蓝色全宽条不再是任何状态的派生结果。

### 7.4 状态与展示优先级

极端情况下多个触发事件接近发生，展示按以下优先级收敛：

1. 无安全快照的 `Initial` 或 `AccountSwitch`：内容区骨架/错误状态。
2. `ManualRefresh`：刷新按钮反馈。
3. `Search / Filter / SourceSwitch`：对应上下文反馈。
4. `Append`：列表底部反馈。
5. `BackgroundRefresh`：默认静默。

同一个请求只能选择一个主反馈位置，避免搜索框、工具栏和列表底部同时转圈。

## 8. 请求并发与数据提交

### 8.1 最新请求获胜

保留当前 request ID 防护：

1. 每次有效查询生成递增 ID。
2. 结果、错误和加载完成只能修改与当前 ID 相同的状态。
3. 旧请求完成时直接丢弃，不提交数据，也不结束新请求的转圈。
4. 延迟计时器绑定请求 ID；请求被替换或组件卸载时必须清理。

云端请求若现有封装容易接入 `AbortController`，可以将取消作为后续优化；本次正确性不能依赖真实网络取消。

### 8.2 用户操作优先于后台刷新

- 用户搜索或筛选进行中时，本地索引事件不得启动一个并行的可见刷新。
- 后台事件可合并为一次尾随刷新，在当前用户请求提交后执行。
- 尾随刷新仍然静默，并且必须使用已经提交的最新查询条件。
- 手动刷新进行中时禁用重复刷新，避免同一按钮同时代表多个请求。

### 8.3 旧结果可交互边界

同来源、同账号作用域的旧结果在重新校验期间保持可交互：

- 允许预览、打开、复制路径及进入已有详情。
- 具有删除等影响的操作继续使用自身已有权限检查与确认流程。
- 不增加覆盖层，不统一设置 `pointer-events: none`。
- 新结果提交时以稳定资源 ID 重新计算选中项；不存在的选中项再清除。

来源或账号作用域发生变化时，绝不能以“旧结果可交互”为由展示跨作用域数据。

## 9. 滚动、焦点与布局

### 9.1 滚动规则

| 操作 | 请求开始时 | 成功提交时 |
| --- | --- | --- |
| 搜索/筛选 | 保持当前滚动位置 | 滚到结果顶部 |
| 来源/账号切换 | 切换到目标内容容器 | 滚到顶部 |
| 手动刷新 | 保持 | 保持；对已消失项目做最小校正 |
| 后台刷新 | 保持 | 尽量按稳定资源 ID 保持锚点 |
| 分页 | 保持 | 保持，项目追加到底部 |
| 请求失败 | 保持 | 保持 |

滚到顶部只在最新请求成功提交后执行一次，不能在防抖开始、转圈出现或旧请求完成时执行。

### 9.2 焦点规则

- 搜索请求开始和结束都不能使输入框失焦。
- 结果提交不能把焦点强制移动到列表首项。
- 筛选弹层在选项确认后按现有规则关闭，加载反馈不抢焦点。
- 刷新按钮结束旋转后仍保留键盘焦点。

### 9.3 布局稳定性

- 搜索图标与转圈使用相同容器尺寸。
- 筛选状态槽在空闲态也保留宽度。
- 加载状态不插入或删除工具栏下方的 2px 区域。
- 结果替换前后保持内容容器尺寸，不额外插入顶部占位条。

## 10. 错误、空状态与重试

### 10.1 有旧结果时失败

- 停止对应转圈。
- 保留旧结果，不切换为空状态。
- 显示现有错误提示或轻量错误条，文案明确为“结果未更新”，避免用户误以为列表匹配当前条件。
- 重试必须携带当前最新查询条件，不能复用失败请求创建时已过期的条件。

### 10.2 无旧结果时失败

- 停止骨架。
- 显示现有整页错误状态和重试入口。
- 不把请求失败解释为“暂无文件”。

### 10.3 恢复

- 后续查询成功后清除上一次可恢复错误。
- 用户修改搜索词或筛选条件即创建新请求，不需要先手动关闭错误提示。
- 后台刷新失败不能覆盖一个正在成功显示的用户查询状态。

## 11. 可访问性

- 活动内容容器在用户可感知请求期间设置 `aria-busy="true"`。
- 转圈图标本身设置 `aria-hidden="true"`，避免读屏重复朗读。
- 使用单一 `role="status"`、`aria-live="polite"` 区域播报长等待状态。
- 200ms 内完成的请求不播报“开始/完成”，减少读屏噪声。
- 超过 1000ms 时只播报一次；完成后播报“结果已更新”或错误结果。
- 后台静默刷新默认不播报，除非刷新失败且错误会影响当前内容可信度。
- 所有状态不能只依赖颜色表达。
- `prefers-reduced-motion` 下用静态图标与文字表达等待状态。

## 16. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 请求原因分散在多个 effect 中 | 反馈位置与真实操作不一致 | 由统一请求入口记录原因，组件只消费派生结果 |
| 延迟计时器未绑定 request ID | 旧请求可能闪现或提前关闭新转圈 | 每个计时器保存请求 ID，并在替换、完成和卸载时清理 |
| 搜索转圈挤压清空按钮 | 输入框布局跳动 | 左侧图标使用固定容器，清空按钮保留独立区域 |
| 旧结果与当前搜索词不一致 | 用户误以为已是新结果 | 加载时显示上下文反馈；失败时明确标识“结果未更新” |
| 账号切换复用旧云端结果 | 数据泄露 | cloud scope key 变化立即隔离结果，按无安全快照处理 |
| 后台刷新抢占用户查询 | 结果或反馈跳变 | 用户请求优先，后台事件合并为尾随静默刷新 |
| 大型组件继续膨胀 | 后续维护困难 | 仅提取加载展示纯逻辑、计时 hook 和微型组件 |

## 17. 回滚方案

本次没有接口、数据库或持久化格式变化，回滚只涉及客户端展示层：

- 回退触发原因、延迟 hook 和微型反馈组件。
- 恢复原有请求阶段和数据提交流程。
- 若单个上下文位置出现兼容问题，可临时统一回退为工具栏固定状态槽转圈。
- 不建议恢复全宽蓝色条；临时降级也应保留中性、局部、无布局跳动的反馈。

无需数据库回滚、数据修复或服务端发布配合。

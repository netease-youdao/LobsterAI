# OpenClaw 输出预算被估算值耗尽的修复设计

## 1. 概述

### 1.1 问题

长会话使用 OpenAI-compatible 套餐模型时，请求可能正常结束但没有可见回复。
自动续答重复发送相同预算的请求后，最终提示无法生成回复。

问题发生在普通对话请求中。它与摘要章节格式审核失败、摘要生成慢、手动压缩的
客户端等待超时是不同问题。本次只修改输出预算和其溢出恢复边界。

### 1.2 根因

固定版本 OpenClaw `v2026.8.1` 存在两个不同的预算决策：

- 自动压缩可以参考服务端返回的 usage。
- Chat Completions 发送层对最终消息、推理回放和工具定义重新估算字符数，并乘以
  `1.25`。它用 `max(1, contextWindow - estimatedInput - 1)` 限制输出。

当估算偏高时，服务端实际仍有空间，发送层却已把输出额度降到 1。
推理模型可能耗尽这点额度，只返回 `finish_reason=length`，没有正文。
服务端没有返回超限错误，现有压缩恢复便无法处理这次失败。

诊断量级可用合成数据复现：上下文窗口 262144，配置输出 8192，字符估算输入
263233；此前服务端观测到的实际输入约 208000。估算超限不能证明真实请求超限。
测试不包含用户会话内容、身份、凭据或线上请求记录。

### 1.3 上游状态

截至 2026-09-15 的调查：

- [#105729](https://github.com/openclaw/openclaw/issues/105729)：同类的 1 token
  输出耗尽问题，仍开放。
- [#105824](https://github.com/openclaw/openclaw/pull/105824)：提出限制字符估算
  截断的适用范围，已关闭且未合并。本补丁采用相同的适用范围判断，并补充本地
  预算耗尽错误、HTTP 验证以及恢复次数上限测试；不是已经发布的上游修复。
- [#140902](https://github.com/openclaw/openclaw/pull/140902)：补充工具定义的
  预检估算及低输出额度警告，已合并，但保留了 1 token 下限，不足以修复本例。

## 2. 用户场景

| 场景 | 预期行为 |
| --- | --- |
| 实际输入可容纳，但字符估算超过窗口 | 保留正常配置的输出额度，模型可以完成回复。 |
| 实际输入加输出上限超过严格服务的限制 | 接收服务端超限错误，交给现有自动压缩恢复。 |
| 工具定义太大，压缩历史也无法容纳 | 达到现有恢复次数上限后明确报错。 |
| 输出上限本身大于或等于整个窗口 | 继续根据输入估算收缩，兼容 StepFun、vLLM 等配置。 |

## 3. 功能需求

- FR-1：普通请求不因第二套字符估算而逐步丢失已配置的输出额度。
- FR-2：保留调用参数、模型参数、模型输出上限、`contextTokens` 的既有优先级。
- FR-3：保留真正超限时的压缩恢复；不增加无限重试或绕过上下文限制的行为。
- FR-4：必须尊重调用方明确设置的 1、2 等小输出额度。
- FR-5：以固定版本补丁交付，并登记补丁清单及应用结果强校验。

## 4. 实现方案

### 4.1 明确估算值的用途

修改 `packages/ai/src/transports/openai-completions-params.ts`：

1. 先按原有优先级解析输出额度，并执行原有的模型输出上限约束。
2. 对显式代理类端点，仅当输出额度本身 `>= effectiveContextTokens` 时，继续
   用最终请求的字符估算来缩小输出上限。
3. 对常规输出额度（如 8192），直接保留。自动压缩仍使用原有 usage 及压缩策略；
   服务端真实超限仍通过现有错误分类和恢复链路处理。
4. 特殊的大输出配置收缩后若不足 16 tokens，则抛出可恢复的 `Context overflow`
   错误，避免自动构造 1 token 请求。16 是最低可用性保护值，不是足够完成推理
   或回答的保证，也不提升调用方明确指定的小额度。

这个判断**不表示输出上限低于窗口就一定能发送成功**。严格服务仍检查“输入＋输出”
总量，可能先返回一次超限错误，随后执行压缩。修复选择可观察、可恢复的拒绝，避免
把潜在失败变成协议成功的空回复。

不新增跨请求 usage 缓存，也不把上一回合的 usage 当作当前最终请求的精确值。
系统提示、工具定义、历史回放以及模型路由都可能改变；直接用旧 usage 覆盖估算，
需要额外的请求来源与内容一致性证明，超出本次小范围修复。

### 4.2 复用恢复流程

既有 `recoverEmbeddedRunOverflow()` 可以识别兼容服务的超限错误，并调用上下文
引擎压缩。共享恢复状态限制最多 3 次溢出压缩；仍无法恢复则给出可见错误。
本次不修改次数上限、压缩阈值、用户消息持久化或已执行工具的重放策略。

本地估算错误使用 `estimatedInput` 标记，不将其伪装成服务端的实际 token 计数。

### 4.3 交付位置

- `scripts/patches/v2026.8.1/openclaw-openai-completions-output-budget.patch`
- `scripts/apply-openclaw-patches.cjs`：登记强校验，拒绝残留旧的 1 token 截断公式。
- `src/main/libs/openclawPatches/v20260801UpgradeDecisions.test.ts`：登记补丁清单。

问题发生在 OpenClaw 的最终请求组装阶段。通过 LobsterAI 的 `onPayload` 再覆盖
字段会复制输出参数优先级及模型兼容规则，因此使用版本补丁修正实际决策点。
需重新构建 OpenClaw runtime 并重启网关才能生效；无配置或数据库迁移。

## 5. 边界情况

| 边界 | 处理及限制 |
| --- | --- |
| `max_tokens` / `max_completion_tokens` | 两种字段均覆盖。 |
| 大工具、中文、结构化输出、推理回放 | 保留内容和正常输出上限；不声称缓存命中不占上下文。 |
| 大输出上限及较小 `contextTokens` | 保留原有严格端点收缩，耗尽时进入恢复。 |
| 服务端真实超限 | 依赖已有错误识别；未知错误格式不保证自动恢复。 |
| 未返回 usage、服务端静默截断 | 本次不实现通用 tokenizer，也不保证修复所有空回复。 |
| 压缩仍然很慢或 UI 等待超时 | 本补丁不修改摘要推理时长及客户端 120 秒等待限制。 |

## 6. 验收标准

- 旧代码运行新增预算用例失败，明确复现 `8192 → 1` 和渐进削减。
- 修复后同一合成请求保留 8192；显式小额度及模型额度优先级不回归。
- 本地真实 HTTP 服务分别模拟约 208000 和 260000 的实际输入：前者产生正文，
  后者产生可识别的超限错误，缩短上下文后用完整输出额度成功。
- 覆盖 OpenAI/vLLM 形式、Kimi 形式、本地预算耗尽错误的 3 次恢复上限。
- 原有严格服务大输出收缩、兼容缓存、推理及请求流测试通过。
- 补丁能与当前 release 的补丁完整叠加；完成相关构建与网关验证并记录实际结果。

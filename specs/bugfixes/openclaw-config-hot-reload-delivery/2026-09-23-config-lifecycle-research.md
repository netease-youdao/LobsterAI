**2026-09-23：套餐模型异常与 OpenClaw 配置生命周期调研**

范围：用户反馈问题 2，结合现场日志、LobsterAI 历史提交、固定的 OpenClaw `v2026.8.1` 源码和上游社区。本文是诊断与改造建议，未实施代码修改。上游状态查询截至 2026-09-23；合并状态以当日 GitHub API 为准，版本包含关系另用 Git 历史核实。

**结论：上游机制确实经历过缺陷和调整；我们当前的集成也没有完成“目标配置最终生效”的保证。** 两者叠加，导致每次围绕超时、重试和重启修复一个局部症状。现在已有可复用的上游机制，建议以它为基础收拢宿主的配置生命周期。

- `config.set` 成功只保证保存。当前宿主仍在这个时点结束配置等待，并向调用者返回成功。
- `config.patch` / `config.apply` 对可热更新的写入有实际应用确认；这项能力已在我们固定的运行时中，无需等上游新增接口。
- 上游后续又修复了配置读取缓存，并让 `commands` 等更多配置无需整网关重启。这些改进不在当前固定版本中，可以减少我们面对的冲突与重启。
- 需要重启、连接中断、环境变量变化和多个配置目标接续到来时，宿主仍要负责跟踪到最终状态。单独替换 RPC 名称不能完成这部分工作。

**当前代码的具体缺口**

1. **有串行队列，但队列任务完成早于配置应用。** [main.ts](../../../src/main/main.ts:3205) 已有 `openClawConfigApplyQueue`、generation 和等待屏障。它们解决宿主调用顺序；`_syncOpenClawConfigImpl` 返回成功后屏障就释放，因此不会覆盖网关仍在进行的应用或重启。
2. **正常 ACK 分支缺少收尾。** [openclawConfigDelivery.ts](../../../src/main/libs/openclawConfigDelivery.ts:185) 在 SET 成功后返回 `Accepted`；交付函数随后结束。[main.ts](../../../src/main/main.ts:3117) 将其转成同步成功。
3. **文件没变化被当成无需继续处理。** [main.ts](../../../src/main/main.ts:3066) 的提前返回没有检查当前目标是否已应用。未应用状态可一直保留到下一次实质配置变更。
4. **运行期有两条写入/通知路径。** [openclawConfigSync.ts](../../../src/main/libs/openclawConfigSync.ts:3314) 先原子换文件，网关 watcher 可以立即行动；之后宿主又交给配置 RPC 写入一次。原子换文件避免半文件，不提供跨进程的条件更新保护，也不能把 watcher 和 RPC 合成一个应用事务。
5. **恢复建议还未变成恢复保证。** 超时和 hash 冲突有局部重试，延迟重启有保护，但普通 ACK 后未应用、文件不变和恢复限流的组合缺少持续待办。

固定版上游的对应实现也很明确：`src/gateway/server-methods/config.ts` 中 set 不要求 application receipt；patch/apply 调用 `shouldAwaitGatewayConfigApplication`。`respondWithConfigRestartWrite` 对未应用结果返回 `UNAVAILABLE`。`config.patch` 还有无变化直接返回的分支，因此保留先写盘再 patch 的顺序，不能自动获得一次实际应用确认。确需重新应用已保存内容时，应遵循上游的 apply/restart 恢复流程。

这里的设计判断是：**“配置生成与保存”加上“最终运行状态的确认”才构成一次可完成的宿主操作。** 更长 timeout 或更多 retries 不能代替这个完成条件。`GatewayConfigReloadSupersededError` 本身只说明旧候选被更新来源取代；真正需要追踪的是最新目标有没有最终生效。

**建议在现有队列基础上完成一次有边界的改造**

第一步统一成功标准和恢复待办。这一步即使暂时继续使用 set，也有独立价值：记录最新目标及影响范围；保存后进入等待应用；超时、断线或冷却期间保留目标；由重连、工作结束和有界重试继续处理。只在目标已应用，或向调用者明确报告失败/等待时结束。已有 `confirmOpenClawConfigApplied` 可复用其部分逻辑，但不能只把一次短轮询接到成功分支后就当成完整方案。

判断必须同时涵盖目标身份与当前网关代次：相等的两个旧 revision 不能证明新目标生效；`hash` 是保存内容的令牌，不能和 `appliedConfigHash` 直接相等比较。后者应与同一快照的 `configRevisionHash` 比较，还要证明该快照确实对应当前目标。脱敏值不应被当成任意内容都匹配的通配符。

第二步收拢运行期写入口，采用上游的应用事务。推荐顺序是：生成目标 → 读取最新 revision → 提交有所有权边界的 RPC → 等待应用/重启结果 → 确认目标 → 放行依赖它的新任务。

- 运行中不先直接覆盖文件。增量变更优先 patch；只有明确拥有完整配置并完成合并时才 apply。
- 准备阶段合并 LobsterAI 管理内容、企业配置、用户或插件拥有的字段。hash 冲突时在新基线上重新合并本次意图，不能仅换一个新 hash 重发旧全量快照。
- patch 的数组与删除语义需要遵循 `replacePaths` 契约。全文 get 返回的脱敏结果不能直接写入文件。
- 停止状态的初始化/迁移可以单独准备启动文件，但下次 ready 仍要确认它对应当前宿主。启动中保留一个最新目标，握手后完成交付，避免不断改盘争抢 watcher。
- 冷却限制的是恢复动作频率，不能清掉尚未完成的目标。连续 A→B→C 应保证最终 C 有结果，旧 B 的失败不能丢掉 C。

第三步明确两层生命周期的分工。普通配置的热更新、内部子系统替换及必要的网关内部重启，尽量让上游生命周期负责；宿主负责子进程启动、退出，以及必须获得新环境或新运行时文件的重新拉起。我们已设置 `OPENCLAW_NO_RESPAWN=1`，无需再把它当作待添加的万能修复。

同 PID 的网关内部重启不会获得新的宿主环境变量；环境变化、某些插件/运行时文件变化不能被“配置 hash 相等”或“WS 已重连”冲销。判断重启意图应结合协议 `shutdown` 事件、`restartExpectedMs`、宿主停止意图和子进程状态，避免只凭关闭码 1012。上游也提供原生忙碌/暂停协作机制；引入时需核实其有界等待和强制行为是否符合 LobsterAI 的“不打断活动任务”要求，不能简单替换现有 IM 保护。

套餐模型的可用条件还应包括当前代理依赖：网关连接成功仅说明 RPC 可用，不能证明其模型请求已使用当前代理。升级启动场景应把代理监听地址、必要环境和目标配置的确认放在模型任务准入之前；对已运行任务保留排空通道，避免配置等待与任务完成互相阻塞。固定代理端口可以降低触发概率，但有端口占用和多实例问题，不是这类故障的完整修复。

**验收应围绕完整链路，而非只验证 RPC 返回值**

1. 宿主重启，代理由 P1 变 P2；网关在慢启动及并发同步下最终请求 P2，确认前不放行受影响的新任务。
2. SET 已返回成功，运行配置仍旧；文件后续无变化。恢复待办继续存在，最终生效或明确报错。
3. patch/apply 热更新成功后，立刻读取模型/执行合成 provider 请求，观察实际新值；注入 preparation 失败时不能报已应用。
4. 配置 A→B→C，B 被 supersede；只需要最新 C 收敛，但不能丢失任何独立的环境/插件进程重建要求。
5. timeout 后迟到 ACK、断线后实际成功、重启先于回应：重连确认，避免重复副作用与双重重启。
6. 原生 IM 准备/执行、cron、桌面任务同时存在：配置恢复不强杀活动工作，工作结束后 pending 继续执行；不因等待应用阻塞原任务收尾。
7. 恢复处于冷却期，之后没有新配置事件：仍会重新处理，不能依靠用户再改一次设置才能恢复。
8. 真正的并发写入及无变化 patch：保留其他所有者字段，正确处理删除/数组、secret 引用；no-op 不等于运行时已收敛。
9. 环境变化需要新进程：同 PID 内部重启和配置相等不能提前满足要求；实际新进程继承目标环境。
10. 另行验证网络失败后的会话重试幂等性。该问题应在上游会话/重试所有者修复，不能通过清空历史或关闭幂等保护绕过。

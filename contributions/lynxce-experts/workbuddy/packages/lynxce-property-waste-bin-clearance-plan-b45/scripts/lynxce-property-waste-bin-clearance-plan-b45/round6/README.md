# 单点垃圾清运第六轮计算器
本地标准库精确分数计算。执行python3 calculate.py normal.json；同输入加--format markdown直接渲染分段表和完整通知，不再重写自由正文。只处理一个点位的升数、全清时点和单班组约束；多点路程与人员安排须先建立对应区间，不能假设同时清两点。bins每桶给nominalL、usableRatio、activeFrom，未可用桶不应列为已启用。segments连续并给每段新增升数；新增桶在段内到位时，不把总量均摊：若按原容量无法保证而新容量足够，capacityFeasible=null，必须补分布。新增窗口位于段中同样先按真实分段重整输入。clearWindows是已允许完成全清的时刻，≤12个；枚举清空子集最少次数，closingClearRequired由用户明确。作业分钟、班组可用窗口、已有占用三项齐全才判staffing，否则容量候选仍标人员待核。actualExecutionStatus与categoryConfirmation仅用户明确来源文字/null，未知不会变成未开始、已清或用户已确认类别。两来源情境独立，jointCompletePlans仅数学共同完整方案，未确认前不自动执行共同部分。零桶不除零，不伪称可行。notice.text为复制全文，characters=len(text)。
并列候选草案：先少趟、再少期末余量、再时间稳定排序，不视为用户已批准目标。
第六轮必要条件直出：diagnosticAllAllowedClears先按每个已允许端点全清，下一段openingL因此不重复累计已清量。每段段初超额=max(openingL−段初容量,0)，段末超额=max(openingL+addedL−段末容量,0)，额外清除必要下界为两者最大值；输出necessaryRemovalConditions及同源Markdown与阻断通知。固定128升且10点已全清，10—12新增130，保留12点清时C≥2，不误写90/92。此C只是累计必要下界，单次只能全清时须核当时已有量及段内分布，不能任取2升或保证充分。段内增桶仍保持原null可行性规则，段末容量只用于必要下界，不追溯证明启用前未溢出。多来源未裁定不自动采用大容量方案。
各段下界均以原诊断余额为基线，不能把多段下界直接相加；新增清除落实后重新递推。

第六轮格式修复：完整9列表格数据行之后强制一个空行，容量候选、守恒、必要条件、通知和字符数均为独立正文段。必须用真实GFM解析器验证表体恰为输入分段数，不能只搜索以竖线开头的行。计算、C≥2必要非充分、所有数据样例均保持。

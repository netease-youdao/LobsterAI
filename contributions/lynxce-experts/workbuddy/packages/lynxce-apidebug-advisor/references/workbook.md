# 可复制联调底稿

```text
问题编号／环境／版本／时间窗：
影响：失败请求/全部请求；受影响用户数；业务结果是否确定。
证据索引：编号｜来源层｜请求标识｜时间或耗时｜原文摘录｜限制。
时间线：客户端→网关→应用→依赖→结果提交→响应。
排查矩阵：层｜候选原因｜支持证据｜反证｜最小验证｜预期观察｜责任角色。
契约：方法路径｜认证方式｜输入字段类型与单位｜成功响应｜失败响应｜版本兼容。
超时重试：各层预算｜可重试条件｜次数上限｜总时限｜幂等作用域及载荷冲突。
修复候选：改动点｜前置条件｜影响面｜验证环境｜回退条件｜数据处理。
回归表：前置状态｜输入和操作｜预期响应｜预期业务副作用｜需要的证据。
结论：已证实事实／候选原因／未覆盖边界／下一行动。
关键问题：最多三条，分别指向会改变优先级的缺口。
```

## 已填假设示例：创建订单超时

示例是脱敏假设记录，不是实际抓包。某十分钟窗口共1000次创建订单请求，其中50次网关返回504，观察请求超时率为50/1000即百分之五；不能由此推断50位用户受损。假设材料给出同一请求的网关持续时间1000毫秒，配置预算1000毫秒；应用记录1200毫秒后完成响应，内部等待依赖900毫秒，其他处理300毫秒。两者相加为1200毫秒，超过网关预算200毫秒。

排查矩阵首项为“预算失配候选”：支持证据是同一请求耗时超过配置；反证需要检查其余49个失败请求是否同样超预算。如果失败请求发生在应用收到之前，该解释便不覆盖它。下一步请运维角色提供网关错误原因及分布，请研发角色查该请求的订单状态。当前不能判断订单是否创建，不能直接建议重发全部50次请求。

示例联调契约假设为 `POST /orders`，输入金额整数 `amount_minor=2500`、币种 `CNY`，返回业务订单号。用户材料确认支持请求幂等键时，同键同载荷重试返回同一订单，同键不同金额按该系统契约拒绝，具体错误码待确认。金额表示25.00单位货币，不能把整数2500直接显示为2500元。

回归行一：在受控验证环境把依赖延迟设为900毫秒，由团队记录端到端耗时及网关结果，验证预算调整是否有效，状态待执行。回归行二：相同幂等键重复提交两次，应只有一笔订单；行三：首次超时后查询业务状态，确认已完成时只取回结果。建议结论为“优先核对预算及副作用，尚未证实全部错误同源”，不是“接口已修好”。

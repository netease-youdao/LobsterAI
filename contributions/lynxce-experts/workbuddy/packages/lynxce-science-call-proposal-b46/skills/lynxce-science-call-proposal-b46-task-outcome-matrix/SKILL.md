# 任务绩效成稿
本能力把拟研发问题写成有检查办法的技术任务、绩效目标和立项申请章节。输入包括本轮指南方向、现有技术及其证据、拟任务、人员角色、实施期和用户指定的交付范围。先区分现状基线、拟目标和已完成成果；对每项任务建立“问题—动作—交付物—测量方法—指标—证据”的链条。目标必须有单位和比较方向；识别准确率越高越好、时延越低越好，不能把“改善”写成没有阈值的目标，也不能替用户证明算法必能达到目标。

正常交付直接形成研究必要性、研究内容与技术路线、现有基础和拟创新点、实施安排、绩效目标五段成稿，不能仅列框架。未知创新对比用待补证据说明，不宣称领先。建议的阶段安排明确为建议，不冒充用户已批准。目标数量、样本结构和检测规则之间不得混淆；五百件样品中一百缺陷、四百正常只说明结构，不能当已达到百分之九十五准确率，更不能把总体准确率当缺陷召回率。用户未给漏检数据，不推导召回率或漏检率。

假设成稿片段：“本项目拟研发一套输送线缺陷检测系统。现有内部记录准确率百分之九十，拟目标不低于百分之九十五，单件处理时延不高于二百毫秒。拟以五百件样品进行验证，样品构成、判定标准、独立性和执行方在测试方案确认后锁定。实施期十二个月，拟按数据规则、算法集成和验证试用三个阶段推进。”这些都是假设项目的计划，不能替换成已经完成或通过检测。

可编辑绩效行写为“指标ID【】；任务【】；基线【数值与资料编号】；拟目标【比较符号、数值、单位】；采样与方法【】；阶段【】；证据【拟形成文件】；责任角色【用户给定或待指定】”。指标变更时保留旧目标、变更理由和批准状态，未获确认不得悄悄降低目标。完成标准为每项指南任务都有实质动作和交付，每个指标有测量口径，成稿不凭空增添机构、专利、客户认可或真实应用效果，更新一个局部条件仍保留其余未变任务与目标。

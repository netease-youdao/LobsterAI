# SQL只读查询与粒度控制

## 输入与结果粒度
接收数据库方言及版本、表结构、键、关联关系、脱敏样例、结果粒度、统计期间及时区。先回答一行结果代表什么，再写查询。订单一行与退款多行不能直接连接后求订单总额；DISTINCT不是解决所有粒度问题的办法，金额相同的不同订单也不能去掉。有效订单、测试记录和退款口径必须由用户定义，不臆造实际数据库存在的状态值。
本技能只交只读SELECT草稿与核对方法，不执行数据库命令，不提供UPDATE、DELETE或维护脚本。修改需求转成受影响范围查询和规则说明，执行与备份交给用户。字段名与版本缺失先给参数模板，所有示例表为假设，不能称用户数据库已存在。
## 方法一：先汇总一对多明细
假设PostgreSQL环境，orders(order_id,customer_id,amount,created_at)，refunds(order_id,refund_amount)。订单键由用户确认唯一，退款在本例代表全部已确认退款且可归属订单；如果真实规则只计某期间退款，需用户另定口径。查询按订单创建期间筛选，退款按所选订单的全部退款汇总，不混淆两种期间。
```sql
WITH refund_totals AS (
  SELECT order_id, SUM(refund_amount) AS refund_amount
  FROM refunds
  GROUP BY order_id
), net_orders AS (
  SELECT o.order_id, o.customer_id,
         o.amount - COALESCE(r.refund_amount, 0) AS net_amount
  FROM orders AS o
  LEFT JOIN refund_totals AS r ON r.order_id = o.order_id
  WHERE o.created_at >= :start_at
    AND o.created_at < :end_at
)
SELECT customer_id, SUM(net_amount) AS net_amount
FROM net_orders
GROUP BY customer_id;
```
:start_at和:end_at是供用户客户端绑定的参数符号，非所有工具原样可执行；须按用户客户端参数机制改写。只有用户确认退款数据完整时COALESCE缺行到0才成立；存在未知退款就先列缺项，不能用该查询冒充完整净额。
## 完整样例与反例
订单O1=C1/100、O2=C1/150、O3=C2/80；退款O1有10和10两行、O3有10。退款汇总O1=20、O3=10，净额80、150、70，客户C1=230、C2=70，总300。直接LEFT JOIN明细后SUM订单会将O1计两次，订单金额错误变100+100+150+80=430；正确原总330、退款30，净300。对账应检查连接后订单行数仍3和订单键唯一，不只比金额是否看着合理。
## 方法二：只读范围与性能分析
用户提出清理重复记录时，先用SELECT键及COUNT(*)、GROUP BY与HAVING COUNT(*)>1列候选，再请用户定义重复含义。不同业务事件共用键不等于错误数据。优化需用户提供脱敏执行计划、数据规模和索引说明；先观察扫描与连接基数、过滤选择度和排序，给候选改写，不宣称索引一定加速。深分页方案需要唯一稳定排序与完整游标，单用id>末ID不能替代任意排序查询。
时间用左闭右开区间避免边界重复，时区输入明确，否则暂停跨期比较。COUNT(*)包含所有行、COUNT(amount)排除NULL，平均值分母据用户规则选择。NULL与空字符串不同，不随意COALESCE覆盖。退款跨期间归属与订单创建期间不同，需明确是订单队列净额还是当期现金收支。
## 输出、异常与验收
查询卡：方言｜假设表结构｜结果粒度｜时间口径｜有效条件｜参数机制｜只读SQL｜对账不变量｜未执行状态。缺主键不能给确定去重结果，材料冲突先列两种规则；分母0显示不可计算。验收核行数、键数、金额和排除数，查询结果只标样例期望。经营数据不构成税务或审计结论，无真实连接不声称已查询、写回或性能验证，文档中代码供审核而非包内可执行脚本。
### 复核顺序
先核样表结构、键与结果粒度，再核有效规则、时间、空值和重复，再核公式或查询，最后核行数、金额与分母。用户确认样例结果不等于真实文件已运行，静态核对与用户实跑反馈分列。原始数据留存，清洗规则可回查；环境变化时先确认函数与方言，不把上一环境通过状态带到当前环境。缺失数据不以0掩盖，对经营结果的解释不超过材料范围。

## 增补实例：队列净额与当期现金不同
上述示例按订单创建时间选订单，然后取这些订单的全部退款，是订单队列净额。若用户要当月现金收支，收入与退款应各按实际收付时间归期，不能照抄订单创建时间条件。真实表是否有收款和退款时间、退款是否已成功，均需用户材料；字段缺失时不补假字段然后说查询已可运行。两种口径可以给定义对照，必须等待用户选定。
空字符串、空值与零金额分别处理，订单金额未知时不自动设为零。退款表没有对应行能否表示无退款依赖数据完整性；源表仅导出部分期间时不能用缺行推无退款。金额列应由用户说明数值类型与精度，不能把浮点结果当精确金额核对。汇总后的取整规则跟经营口径一致，客户端展示位数不等于实际数值已四舍五入。
重复订单键应查询候选记录并展示业务事件、版本或更新时间字段，如果这些字段未提供就保留缺口。不根据最大编号选择“最新”，编号未必按时间增长；若有同时间多行仍需稳定裁决规则。查询性能优化只有执行计划和数据规模能支持判断，写法更短不等于扫描更少。索引建议需明确过滤、关联和排序列以及新增维护代价，不能说所有慢查询都是缺索引。
用户请求修改或删除时交只读影响范围与业务规则，不生成可执行修改语句。查询草稿里的参数占位是适配点，不包装成一键完成；用户必须在自己的客户端按方言绑定参数。回传结果需与脱敏样例、行数、键数和金额对账，未回传则只标静态预期。没有连接日志不写数据库已经验证，通过静态核查的代码也不代表生产性能已通过。

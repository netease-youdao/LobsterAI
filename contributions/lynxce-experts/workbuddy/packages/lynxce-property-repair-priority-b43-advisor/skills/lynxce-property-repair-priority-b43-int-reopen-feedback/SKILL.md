# 维修回访与复发重开记录

以结果证据与复发关联区分维修完成、回访和真正闭环。。输入范围仅限用户给定的建筑物业业务材料；与公开技能分工，独立完成此项中间成果再交专家复核。

## 工作流程

1. 接收工单执行反馈与原报修现象，先分到场、处理结束和结果复核三个节点。

2. 按用户给定验收点整理可观察验证，不生成专业检测参数或现场安全判断。

3. 将住户同意、仍有问题与未回应分类，未回应保持待回访，不填默认满意。

4. 复发时关联原单的设施和症状，症状不同列新问题待核而非强行合单。

5. 建立重开待办与补证问题，保留原处理记录，查明哪项效果未维持。

6. 输出闭环条件表、回访问句与重开记录，待人工确认后再更新建议状态。

## 专属核查方法

- 住户确认针对哪项现象需明确，不能用一次满意覆盖所有工单。

- 人员完成描述与实际功能验证分开，只有照片不等于功能恢复。

- 计算复发时距需两端同一时区，不把发现日期当故障发生时刻。

- 重开工单沿原事件追踪，但统计新报修数与未结事件数应分口径。

## 证据与状态控制

- 先按本任务的复合业务键标记每条材料，保留原值与来源日期，关键字段缺失时只输出可确认部分及补证问题。

- 将输入事实、计算中间值与建议动作分列，复算结果需要能够回到对应单据或记录，不能靠结论倒填来源。

- 用户给定规则只在明确范围内使用，规则变更需记录版本；冲突时列适用条件，不将其他批次或其他任务的规则直接迁移。

- 输出给经办与复核角色审阅，确认资料齐全并不等于业务执行完成，任何现场结果须由用户补充反馈及验证记录。

## 交付与异常

- 输出本任务的领域表格与逐行问题，单位、时间、状态必须写全；没有依据的字段填【待补】，不以零代替缺失。

- 对异常记录给出最小补证动作及其预期证明的条件，不能仅写需要核查，必须说明核哪一项以及结果如何影响表格。

- 先列矛盾与未确认条件，再给条件式建议；存在反证时修订相关行并保留旧版，避免相互矛盾的承诺或计算同时有效。

- 收尾检查表头、合计、状态及来源索引一致，交付文本草案和人工处理清单；不声称联网检测、自动派发或修改系统记录。

## 假设案例

假设工单A周一10:00反馈完成，周一12:00住户确认原现象消失，周二09:00反馈同现象复发。距完成23小时、距确认21小时，两种时距分别列出；原结案记录保留并建议关联重开A-R1。另有工单B仅人员报完成、住户未回应，则两单中具备住户确认记录1单，但A复发后仍需处理，当前可确认闭环数不能直接写1单。

## 能力边界

根据用户提供的资料整理和分析；未知项填【待补】，区分事实、假设与建议。没有实际连接工具时不声称读取或修改业务系统，不编造实时数据或已完成的操作。

# 可复制字典与对账底稿

```text
业务问题／流程版本／证据编号：
漏斗：起点对象／步骤顺序／终点／时间窗／时区。
事件字典：事件名｜语义｜触发条件｜触发端｜次数规则｜分析问题｜责任角色。
属性表：字段｜类型｜必填｜枚举或范围｜单位｜空值含义｜权威来源｜假设样本。
身份规则：匿名标识／登录标识／合并条件／无法关联时的口径。
去重规则：事件唯一键／业务唯一键／保留策略／重试行为。
漏斗表：步骤｜入组对象数｜到达数｜上一步转化率｜总体转化率。
对账表：阶段｜输入数量｜本阶段互斥排除｜输出数量｜证据｜残差。
验收表：场景｜输入｜预期次数及属性｜提供材料｜责任人｜待验收/已获证据。
迁移表：旧定义｜新定义｜消费者｜并存期｜停用条件｜回退方向。
结论：可评审项／不可判定项／下一步；末尾最多三个关键问题。
```

## 已填假设示例：结算漏斗

假设材料包含同一天同一批1000个去重用户的结算页记录，800人点击提交，500人对应有效创建订单，470人完成支付，均处于约定的当天窗口。事件分别为 `checkout_viewed`、`checkout_submitted`、`order_created`、`payment_succeeded`。前两项由客户端记录，后两项依据示例业务服务日志；这仅是假设职责，不代表用户系统已经实现。

提交到创建的转化率为500/800即百分之六十二点五，创建到支付为470/500即百分之九十四，全程为470/1000即百分之四十七。示例中的人数均取自同一入组集合；若“500”实际是订单笔数，必须停止这张用户漏斗并统一分析单位。

支付事件假设有520条原始投递，同一事件标识重试20条，去重后500条；在剩余集合排除测试订单20条，再排除窗口外10条，得到470条。业务表核对也为470笔且一人一笔，所以计数一致，但计数相同不能证明逐键完全一致，还需比对订单键集合。属性样例为订单键 `demo_order_01`、金额整数1990、币种 `CNY`、结果 `succeeded`、事件时间与接收时间分别记录。金额1990表示19.90单位货币，仅用于演示金额口径。

开发验收行填写“重试两次仍使用相同事件标识，原始两条、分析一条；需提供样本负载与去重后记录，状态待验收”。版本迁移行填写“旧支付事件只代表前端跳转，新事件代表业务确认，双读期分别展示，不直接拼接历史趋势；业务和数据角色核对后决定旧事件停用”。这样即使尚无平台权限，也可先交可评审的字典与验收任务。

# 可复制研发交付底稿

```text
需求与版本：编号｜用户行为｜非目标｜材料依据｜验收条件。
方案比较：方案｜实现范围｜一致性｜失败模式｜恢复能力｜取舍理由。
评审单：发现编号｜严重级别｜代码位置/片段｜触发输入｜交错顺序｜后果｜建议。
测试矩阵：用例编号｜关联需求/发现｜前置数据｜动作｜预期响应｜副作用断言｜证据状态。
追溯表：需求→方案风险→代码发现→用例→执行证据；未覆盖项说明原因。
交付门槛：关键行为｜异常恢复｜兼容数据｜灰度观察｜回退限制｜待确认项。
复盘：摘要｜影响｜时间线｜证据支持的机制｜防护缺口｜行动与验收。
结论：已确认／条件成立／待材料；最后最多三个关键问题。
```

## 已填假设示例：库存一件的并发下单

假设需求R01为“库存一件最多创建一笔成功订单”，R02为“同一请求重试不重复创建”。示例代码逻辑是读取库存到局部变量、若大于零则写回局部值减一并创建订单；明确假设没有额外锁、事务串行保护或唯一约束。这不是对用户真实系统的结论。

发现F01为必须修复：请求A读到1，请求B也读到1；A写0并创建订单A，B按自己的旧值写0并创建订单B。最终库存0，成功订单2，超过初始库存1件，超卖1件。这里不是库存负数，错误在两次成功都消费了同一库存。若真实数据库存在可阻止该交错的机制，则需依据完整材料重新评审。

方案甲是在符合具体数据库能力的事务内使用带库存条件的原子更新，并仅在成功取得库存时创建订单；方案乙是按库存单元串行处理命令，同时处理重复消息和队列失败。甲实现范围较集中但需核对事务与冲突重试，乙改变调度并增加队列维护。仅演示取舍，具体语法和性能材料待确认。R02还需独立的幂等键约束，解决库存争用不自动解决请求重复。

用例T01关联R01和F01：初始库存1，两个不同请求在读取阶段交错，预期成功订单最多1、库存不小于0、失败请求有契约响应。T02关联R02：同一键同载荷连续或并发重放，预期只有一笔订单；不同载荷同键按已确认契约拒绝。T03为初始库存0，预期零订单。三条用例状态均为未执行，不能写测试通过。

复盘假设一轮高峰有120个请求，其中8个重复业务订单，重复率按请求口径8/120约百分之六点六七，受影响用户数仍未知。优先行动是补交错调度用例、核对事务边界、加入业务重复结果核对。交付结论为“失败路径在示例假设下成立，方案与用例已可审查；真实约束、运行结果和发布状态待材料”。

# 联调验证与回退交接


## 将候选原因变成可证伪计划
输入候选假设、可用测试环境、设备规模、允许窗口与用户确认的验收标准。每项验证只改变一个主要条件，先预测支持与推翻假设时分别应出现什么记录。假设是“重复发送导致业务重复”，则请求发送序号、服务唯一键和业务记录数；只有发送尝试增加不能证明业务重复。所有执行人和权限由用户确认，不填写已经实施。

假设一百条唯一消息、共一百二十次尝试、服务收到九十五条唯一、业务入库九十三条。唯一到达率九十五除一百为百分之九十五，入口到业务通过率九十三除九十五约百分之九十七点八九，总链路成功九十三除一百为百分之九十三。五条未到入口与两条入口后未入库分别列，不合并成网络丢七条。若报文序号范围其实只代表九十条生成消息，原分母一百应废止，需重新统计，不能保留好看的成功率。

试点计划以用户定义的标准为准。四十台中两台试点占百分之五，计划观察二十四小时；若典型故障周期七十二小时，则一天无错不足验收，应请求覆盖周期。交接模板为变更项、候选原因、基线、测试条件、材料记录、预期、失败分支、人工回退负责人和停止条件。达到阈值也只代表所测窗口，不保证全场景稳定。涉及生产升级、接线与安全动作，交给现场负责人，不给危险步骤。输出未执行的计划与验收空表，获得真实记录后再逐条标通过、未通过或不可判断。


## 联调范围与证据模型
本专家分析用户已有的设备日志、协议说明、拓扑和测试记录，交付排查假设与验证计划，不连接设备，不执行命令，不声称测量过电压、抓过报文或升级过固件。输入首先包括设备型号与硬件修订、固件版本、网关版本、连接方式、部署环境、问题开始时间、影响台数和可脱敏的日志。日志中的密钥、令牌、用户标识和地址应由用户移除；保留稳定的匿名设备编号以便跨文件关联。没有版本号时不能把不同版本的错误混成一个缺陷。

把事件记录拆成设备生成、发送尝试、链路确认、服务接收、业务入库五个位置。每个位置都有时间戳、序号、会话标识和状态含义，缺位置就写未观测。序号连续不代表每次都上报成功，重复报文不代表重复业务记录，设备缓存量不等于云端丢包数。日志里的超时只说明该记录未在规定时窗完成，不直接证明物理断线。物理、链路、协议、应用和服务五层是分类框架，不要求用户冒险做电气操作；先从已有证据覆盖率判断哪层能排除，无法判断的留为候选。

时间对齐尤其重要。记录每种日志的时区、时钟来源、单位、是否单调时间、同步偏差与重启点。若设备时间落后服务三十秒，先保留原时间再创建校正时间列；校正来源必须是用户提供的同步事件，不能凭看起来相似的记录随意平移。重启后序号从零开始时，需要用会话标识与设备编号组成关联键。对丢包率必须区分发送尝试、唯一消息和业务成功，分母为零则不可算。出现采样窗口不重叠就停止端到端率比较，只做各自窗口描述。

固件变更计划从用户给出的测试约束出发，列版本矩阵、验证项目、观测时窗和人工回退条件。本包不附升级功能，也不提供带电接线、绕过保护或生产写入步骤。涉及强电、机械、消防、建筑现场等安全事项，只整理已有材料并交给具备相应能力的现场人员判定；日志分析不能作为安全执行证明。用户要“直接修好”时，说明现在能提供的是可复核假设与人工实验清单，需要真实反馈才能收敛根因，不能虚构设备恢复在线。

排查结论按证据强度写：观察到的现象、能排除的假设、仍可能的因素、下一项最小验证及结果分支。不能因为一次重启后正常就宣布问题修复，需对齐用户给出的复现周期和覆盖设备。交付应包含数据质量、事件时间线、假设矩阵、协议差异、验证计划与验收待办；每个建议标成本、所需材料、由谁执行和停止条件。没有联网工具时不报当前厂商缺陷公告或最新固件，只请求用户提供发行说明和对应日期。

## 与其它环节的交接

本项只负责标题所指任务，输出时列材料编号、已确认结果、尚未确认的字段及后续环节。不能把父专家其它技能的工作当作已经完成。使用[专用模板](../../references/templates.md)中对应表格，父专家的[案例卡](../../references/cases.md)规定任务整体的正常、缺资料、冲突、边界和超能力判据。所有例子是静态假设，未模型实跑；用户应把实际反馈填入空表后再复核。

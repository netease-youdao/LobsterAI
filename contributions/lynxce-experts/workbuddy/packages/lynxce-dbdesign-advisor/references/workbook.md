# 可复制数据库评审稿

```text
评审对象／引擎版本／环境／材料编号：
业务关系：实体｜主键｜关系基数｜唯一作用域｜删除语义。
字段表：字段｜类型与范围｜单位｜空值与默认｜依据｜问题及影响。
约束表：约束｜业务规则｜重复或孤儿检查｜存量处理｜待确认项。
查询表：查询编号｜过滤排序分页｜参数范围｜返回量｜现有索引｜计划证据。
候选表：索引列顺序｜目标查询｜可能收益｜未覆盖查询｜写入存储代价｜验证方式。
迁移表：阶段｜进入条件｜动作草案｜完成证据｜中止条件｜恢复方向及限制。
验证表：环境数据｜查询输入｜读结果｜计划扫描量｜写入及复制影响｜证据状态。
结论：可评审项／暂缓项／下一材料；关键问题最多三个。
```

## 已填假设示例：租户订单列表

假设订单表1000000行，租户内订单号唯一；查询限定某租户和 `status=paid`，按创建时间倒序取100条。用户材料假设为某支持普通复合索引的数据库，并给出同一数据快照下实际扫描10000行、返回100行的计划。扫描返回比为10000/100=100。候选为以租户、状态、创建时间为序的复合索引；排序方向、覆盖策略与具体创建语法须根据真实引擎版本确认，不能仅凭这个顺序保证最优。

假设同环境复测材料显示扫描120行、返回100行，比值为1.2；扫描减少比例为(10000-120)/10000即百分之九十八点八。这里只能说明该计划的扫描量变化，不代表端到端耗时改善同样百分比。若写入吞吐从每秒1000次降到950次，下降百分之五，需与业务可接受阈值比较，阈值尚无材料则不判上线通过。

另一个变更为增加订单来源字段。迁移底稿填写：先扩展兼容列；按稳定订单标识分批回填；逐批核对总数、空值与取值；新应用读新字段但保留兼容；观察后再清理旧逻辑。假设需回填1000000行、每批5000行，恰好200批；每批重试不得重复更改业务含义。处理速率和总耗时均待测，不把200批换算成保证工期。若回填后有2000行仍未知，则未知比例为百分之零点二，保留未知语义并调查来源，不能统一补成某个渠道。

结论为“复合索引值得受控复测，扫描量证据支持继续评审；写入影响与锁等待未通过确认”。负责角色包括业务定义人员、数据库维护人员和应用开发人员，各自需要补唯一性范围、实际计划及迁移兼容证据。

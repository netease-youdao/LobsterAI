# 可复制值班底稿

```text
事件编号／服务／版本／时区／当前状态：
影响：业务路径｜受影响范围｜窗口｜失败/总数｜数据风险｜证据。
分级：团队等级｜判断依据｜待确认阈值｜协调与技术角色。
时间线：异常开始｜发现｜缓解｜恢复；逐项附材料。
候选处置：目标｜前提｜步骤草案｜预期观察｜中止条件｜恢复方向｜执行角色。
恢复核对：业务路径｜错误延迟｜积压｜数据一致性｜观察窗口｜实际证据状态。
交班：未完事项｜已知限制｜下一动作｜责任角色｜下次核对时点。
复盘：触发事件｜机制证据｜防护缺口｜最多三项改进及验收。
下次输入：最新告警摘要／处置记录／业务验证／未决材料。
```

## 已填假设示例：订单查询故障

假设材料记载10:00开始异常、10:03值班发现、10:15临时缓解、10:20关键查询恢复，均为同一时区。业务影响持续20分钟，发现延迟3分钟，发现到缓解12分钟，发现到恢复17分钟；这些是单次事件时长，不称为多次事件平均指标。窗口内20000请求中600次失败，观察失败率600/20000为百分之三，受影响用户数未知。

假设最近有一次查询配置变更，处置候选为恢复上一版配置。支持材料只有变更时间与异常接近，因此先标候选相关，不能直接断言根因。评审稿要求确认旧配置仍兼容当前版本、确认恢复操作范围，并由维护角色在适当环境检查。示例已提供的恢复证据是假设连续十次关键查询成功、错误趋势回落且积压清零；十次样本仍不能证明所有用户已恢复，需要业务角色确认约定观察窗口。

交班稿填写“查询路径已获局部恢复证据，用户影响统计仍待补；下一班核对同一时间窗的用户去重计数和完整观察记录，未确认前不写全部恢复”。周复盘假设五次告警中三次需要人工动作，两次为重复通知，则可行动比例为3/5即百分之六十；是否合并重复通知还要核对它们是否覆盖不同故障，不直接关闭两条告警。

行动单为“维护角色补齐配置回退前的兼容检查，下一次演练提交操作前后业务结果”；“业务角色定义查询恢复观察窗口并提供样例记录”。此处所有时刻与结果均为假设演示，实际状态必须由用户提供材料更新。
